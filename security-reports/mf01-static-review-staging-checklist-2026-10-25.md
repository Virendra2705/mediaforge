### Controls versus network facts

**Confirmed in source:** yt-dlp receives a proxy argument in the reviewed metadata/download invocations; production configuration validation requires a proxy URL and provisioned yt-dlp path. Node callers that use `requestSafeHttp` receive application-layer URL/DNS/redirect validation and pinning. Some failures trigger provider or direct-Node fallbacks. FFmpeg inputs in reviewed conversion code are local files.

**Not established by source:** actual proxy identity or ACL, proxy DNS behavior, network-layer default deny, direct IPv4/IPv6 denial, controls over UDP/QUIC/DNS/alternate ports, coverage of every extractor helper, deployed revision/config parity, and whether a compromised or misconfigured child can open a socket. Environment variables and `--proxy` do not prove these facts.

## Source-level follow-ups for separately authorized remediation

1. `getYtDlpChildEnvironment` starts by copying the complete parent environment and removes only proxy variables. This means any credentials present in the app environment are potentially inherited by yt-dlp. Reviewed FFmpeg/FFprobe `execFile` calls omit an explicit child environment and inherit the Node environment as well. Actual configured secrets were not inspected. A future design should give media tools a minimal allowlisted environment and isolate credentials outside the media process.
2. Existing regression coverage reportedly asserts preservation of an unrelated child environment variable; a least-privilege environment change would require revising that test intentionally.
3. `server/outboundHttp.ts` IPv6 public-address classification accepts the `2000::/3` global-unicast aggregate while excluding selected special ranges. The reviewed exclusion logic appears not to reject all IANA special-purpose/reserved ranges within that aggregate, including documentation space `3fff::/20`. This is a potential app-level classifier gap, not proof of reachability. Compare against the current [IANA IPv6 Special-Purpose Address Registry](https://www.iana.org/assignments/iana-ipv6-special-registry) and add offline regression cases in a separately authorized remediation.
4. RapidAPI fallback after yt-dlp errors can mask a proxy outage by switching to Node direct transport. Decide explicitly whether metadata/download should fail closed when the required media proxy is unavailable, while preserving any independently approved provider API traffic.
5. Verify the `ensureYtDlpBinary` call graph and the non-production curl provisioning branch before staging. Do not make a hostname allowlist for arbitrary extractors as a substitute for isolation; that can break legitimate APIs/CDNs and still miss destinations.

These observations are review candidates only. No source was changed.

## Staging acceptance matrix

Use an authorized isolated worker and operator-owned fixtures only. Fixtures should be local or controlled by the operator: synthetic DNS zone, harmless HTTP(S) origins, redirectors, IPv4/IPv6 sink services, and a recording filtering gateway. Do not target real private networks, cloud metadata services, or third-party hosts. “Required logs” below must be redacted and correlate a test ID, policy version, process/container identity, decision, protocol/address family, and timestamp; never retain cookies, credentials, signed URLs, tokens, or raw media URLs.

For all rows: a test is **inconclusive** if only application-level error output exists. A pass requires a network-level deny/allow record tied to the exact worker/process context plus controlled sink evidence. Do not treat inability to run IPv6, UDP, or a helper process as a passing denial.

## Evidence bundle required before MF-01 closure

1. Revision and artifact identity: source commit, container/worker image digest, yt-dlp/FFmpeg versions, deployed service/worker identity, test timestamps, and test harness version.
2. Effective policy: redacted gateway policy/config hash and version, resolver settings, allowed protocols/ports, worker egress firewall rules for both address families, and operator ownership/attestation. Do not include credentials.
3. Per-test records: test ID, fixture identity, process/network namespace identity, expected and observed result, gateway allow/deny event, network firewall event, and fixture access log. Preserve enough correlation to show that denied traffic never reached the sink.
4. Coverage: yt-dlp metadata/download and extractor secondary requests; Node provider/direct-media fallback; FFmpeg/FFprobe and descendants; DNS, TCP, IPv4, IPv6, UDP/QUIC, redirects, address changes, and alternate ports.
5. Secret handling: redaction policy and evidence that logs/artifacts contain no cookies, authorization headers, API keys, signed URLs, raw user URLs, or tokens.
6. Parity proof: documented match between tested staging policy/artifacts and the intended deployed environment. A staging pass alone cannot establish production configuration.
7. Review sign-off by the authorized application, proxy, and network-policy owners. If any path, protocol, address family, helper, or policy mapping is missing, keep MF-01 open.

## Unresolved questions

- What proxy product/version and operator are intended, and does it enforce DNS-safe destination and port policy at connection time for every hop?
- Can the eventual worker platform deny direct IPv4 and IPv6 from the media process while allowing only the filtering gateway? Can it control DNS, UDP/QUIC, and alternate ports?
- Which provider/API hosts and media CDN/fragment behaviors must remain supported, and what gateway policy can accommodate them without an unsafe broad-public policy or a brittle hostname allowlist?
- Which provider fallbacks should remain available during proxy outage, and should the media operation fail closed instead?
- Which runtime credentials are currently present in the app parent environment? They were intentionally not inspected. Can the media worker run without those credentials?
- Is the non-production curl provisioning branch reachable in any staging profile? Is `ensureYtDlpBinary` invoked in deployment outside the callsites found?
- Does the eventual staging environment have IPv6, raw egress-policy control, process attribution, and auditable gateway/firewall logs?
- What exact deployed artifact and network policy would production use, and who can attest parity?
