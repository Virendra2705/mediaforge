# MF-01 free-only staging infrastructure selection

**Review date:** 2026-10-25  
**Decision:** **MF-01 OPEN — BLOCK RELEASE**  
**Scope:** Read-only repository and official-documentation review. No infrastructure, firewall rules, application files, production services, or tests were changed or exercised.

## Recommendation

The best genuinely free candidate is an **already-owned, operator-controlled Linux host or VM** on which the operator has root or equivalent network-administration authority and can create an isolated media network. No such suitable host was established in this review. The current environment is Android/Termux running as an unprivileged app; although some networking command names exist, this environment has no Docker/Podman, QEMU, KVM device, or `nft`, and the repository notes that the available `iptables` executable does not grant firewall privileges. It is not a suitable enforcement lab.

Therefore, **there is no currently verified staging resource that meets all constraints**. If the operator already has a separate rootful Linux system with no incremental charge, confirm that host and its authorization first. If not, do not silently substitute a free trial, payment-card-backed tier, or proxy-only setup; keep release blocked until the no-cost constraint changes or a suitable existing host is identified.

A local lab can prove the mechanics of isolation and gateway behavior on that host. It cannot, by itself, prove that a future production provider has no unreviewed egress routes, metadata exceptions, control-plane paths, or policy drift.

## Repository and current deployment evidence

Read-only inspection covered `Dockerfile`, `package.json` scripts, `SSRF_EGRESS_LIMITATIONS.md`, and the existing MF-01 infrastructure, worker, and staging proof reports. No `.env` file or runtime environment value was read. No Render manifest, Compose configuration, or repository-managed firewall policy was found.

The Dockerfile installs yt-dlp, FFmpeg, and FFprobe in one Node application image, builds the application, and starts `server-build/server.cjs` as user `node`. It contains no network namespace, egress firewall, filtering gateway, or worker isolation. Package scripts include build, start, test, and lint commands; none were run for this planning task.

`SSRF_EGRESS_LIMITATIONS.md` and the prior MF-01 reports state that `YTDLP_PROXY_URL` is passed to yt-dlp, but that application setting does not block direct sockets. yt-dlp resolves and follows redirects and makes extractor, fragment, and CDN requests itself. The guarded Node HTTP transport is a separate path and does not constrain child-process sockets. Existing reports also identify Node-side media/fallback paths that must be inventoried separately during a later migration.

## Minimal staging architecture (for a later authorized lab)

1. **Control plane:** Keep the existing application/control plane separate. It submits fixed-schema jobs and receives bounded status/results. It never supplies arbitrary gateway destinations, worker shell commands, or storage targets.
2. **Media sandbox:** Run yt-dlp and FFmpeg under an unprivileged identity in a dedicated network namespace or VM with no host networking, no general DNS route, no cloud credentials, and no secrets. The media process can connect only to the gateway’s fixed private address and required proxy port. A host/hypervisor firewall enforces this for both IPv4 and IPv6, regardless of child proxy environment variables. FFmpeg should have no network allowance unless a documented feature requires it.
3. **Filtering gateway:** The gateway resolves through a controlled resolver, validates all A/AAAA answers, rejects any unsafe or mixed answer set, and dials the selected validated numeric address directly (connection pinning). It records enough sanitized evidence to compare the checked address with the actual socket peer. Each redirect and each new extractor/CDN connection is checked afresh. Restrict to explicitly supported HTTP/HTTPS proxy semantics and ports; deny SOCKS, raw TCP, FTP, UDP, QUIC, DNS/DoH, and unknown protocols unless a later documented need is approved and tested. Gateway egress itself needs a host/provider boundary and no general route for the media process.
4. **DNS and fixtures:** The sandbox cannot query public DNS directly. Use operator-controlled DNS fixtures and HTTP/TLS sink endpoints. Test forbidden-address classification with synthetic fixtures and controlled lab routes; never probe real internal services, metadata IPs, or third-party targets.
5. **Node paths:** Inventory and test Node-side API fallbacks, metadata fetches, media stream fallback, diagnostics, previews, and startup probes separately. A Node-side pinned transport is not proof about yt-dlp. Either keep each fixed-host path under its existing guarded transport with separate tests, or move user-influenced media fetches into the same restricted worker/gateway. There must be no fallback from a gateway or DNS failure to direct fetch.
6. **Logging:** Emit only request/job correlation IDs generated for staging, fixed outcome enums, protocol/port categories, duration, policy decision, and sanitized test case IDs. Never log source URLs, query strings, cookies, authorization, proxy credentials, signed URLs, titles, IP addresses, or raw exceptions. Store test evidence with access controls and short retention.

This is a design, not an instruction to change the current app or host. A broad “public Internet allowed” rule is not a strict destination allowlist and does not itself prevent SSRF to public services. A finite media-host allowlist may break extractor/CDN support; any such product tradeoff needs an explicit supported-platform decision.

## What a local result proves—and does not prove

A local lab can demonstrate that its tested kernel/host firewall, namespace, gateway build/configuration, DNS fixture behavior, and actual yt-dlp/FFmpeg processes obey the policy for the tested cases. Preserve sanitized firewall rules/counters, gateway version and config hash, process namespace identifiers, controlled DNS answers, checked-versus-peer evidence, sink logs, and test outputs.

It does **not** establish that Render or another future provider enforces the same rules, that cloud metadata/control-plane paths are contained, that all supported real extractors/CDNs work, that production has matching policy, or that deployment drift is prevented. Production approval requires the same evidence in an authorized staging environment using the selected production-equivalent provider/network boundary, plus configuration review of the deployed revision and every Node/worker process path. Render’s currently reviewed public docs do not establish a service-level outbound destination firewall.

## Next authorized step and release gate

The smallest next step is for the operator to identify and confirm an already-owned, authorized rootful Linux host/VM with no incremental cost and to verify that it supports a host-enforced IPv4/IPv6 boundary outside the media identity. This is an availability/entitlement confirmation only; do not modify it yet. If no such host exists, the current hard constraints leave no verified staging option, so keep MF-01 open and decide whether to authorize a separately funded environment or continue to defer release.

Close MF-01 only after authorized production-equivalent staging proves both address-family direct-egress denial, gateway ACL and DNS/socket pinning, redirects and secondary extractor/CDN traffic, protocol/port bypass denial, fail-closed gateway outage, child-process containment, Node-path behavior, and redacted logs—and the owner verifies the production deployment matches that tested boundary. **MF-01 remains OPEN — BLOCK RELEASE.**
